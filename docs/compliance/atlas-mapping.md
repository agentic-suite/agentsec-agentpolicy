# MITRE ATLAS Mapping

Every agentpolicy rule pack is tagged to **MITRE ATLAS** techniques ([atlas.mitre.org](https://atlas.mitre.org/)),
so a SOC can correlate policy decisions with the adversary model it already uses. The tag lives on the rule pack
(`metadata.yaml`) and the decision event; this table is generated from those tags.

## Rule pack → ATLAS technique

| Rule pack | ATLAS technique (representative) | Why |
|---|---|---|
| destructive-commands (Replit rule) | **AML.T0049** — *Data Destruction* / impact | Irreversible destructive actions |
| secret-in-output | **AML.T0057** — *Exfiltration via AI* / LLM data leakage | Secrets/PII leaving through output |
| exfil-sink | **AML.T0057** — exfiltration to an external sink | Taint-lite egress blocking |
| mcp-allowlist | **AML.T0010** — *Supply Chain Compromise* (tool/MCP) | Poisoned/shadow/unknown MCP servers |
| scope-escalation | **AML.T0055** — *Privilege Escalation* | Out-of-scope actions / step-up |
| rate-budget | **AML.T0049** / resource exhaustion | Runaway autonomy / volume misuse |
| iam-admin (v0.2) | **AML.T0055** — Privilege Escalation | Role/key grant |
| network-egress (v0.2) | **AML.T0057** — Exfiltration | SSRF / unknown-host egress |

> ATLAS's agent coverage is still thin; agentpolicy contributes its incident-anchored packs back as
> ATLAS-style mappings (a small contribution to the ecosystem).

## How the mapping is produced

1. Each rule pack declares `atlas: [AML.Txxxx, ...]` in `metadata.yaml`.
2. `agentpolicy pack validate` checks the technique IDs against the ATLAS list.
3. The release coverage matrix is generated by walking the shipped packs.
4. A decision event carries the technique tag, so SIEM correlation is one field.
